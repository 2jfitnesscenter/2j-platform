# 2J-078B — Shared person identity and Training contract foundation

## Objective

Prepare Platform's backend boundary for the approved Platform ↔ Training identity contract. `personId` is the opaque, immutable, lifetime-stable shared human identity. Platform owns optional client/staff facets; Training identifies an account only through `personId` and its own opaque `trainingUserId`.

## Acceptance criteria

- Persist a person identity independently from client and staff records; allow one person to have both local facets and enforce that each facet belongs to at most one person.
- Define strict V1 `PlatformSubject`, `LinkProposal`, `AccessGrant`, and `TrainingSummary` contracts scoped by `personId`.
- Persist canonical local link identity, uniqueness, version, lifecycle timestamps, and append-only actor audit. Revocation is addressed by `personId`. A local `active` record is synthetic and is never evidence of Training acknowledgement.
- Protect all identity operations server-side with `identity.people.manage`; no role, client ID, or staff ID is accepted from headers as authorization.
- Do not copy central client/staff identifiers, profile data, permissions, or email/phone matching rules into Training.
- Keep provider traffic off by default. Training link create/revoke APIs are separately gated by `trainingLinkingEnabled`, which defaults to false and has no environment-variable opt-in. When disabled they return `423 training_linking_disabled`; enabling this local foundation gate does not enable provider traffic. The read adapter is fail-soft, deadline-bound, and independently requires explicit configuration and an injected signer before any request.
- `explicit_admin` records only the local administrative action; it is not proof-of-possession and must never be represented as `user_confirmed`.
- No SSO, session handoff, access enforcement, payment/booking policy changes, UI, Training repository edits, or real credentials.
- Tests cover contract strictness, fail-soft/off behavior, server authorization, idempotent migration, immutable identity, link lifecycle and audit.

## Implementation boundaries

Platform-only additive PostgreSQL migration; existing client/staff IDs and product behavior remain unchanged. Training remains a separate future implementation following the confirmed contract.

## Lifecycle boundary

- Identity foundation: implemented.
- Local canonical link storage: implemented, but synthetic link creation/revocation is behind the explicit server option and defaults OFF.
- Training LIVE linking/provider traffic: OFF.
- Remote lifecycle/acknowledgement, dual proof, SSO, and Training-side access enforcement: not implemented.
