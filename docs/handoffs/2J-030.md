## Delivered in this correction pass

- Template start/end dates are returned as `YYYY-MM-DD` and compared as ISO date strings at both boundaries. Templates can be explicitly archived; generation stops, the action is audited, and service/area archival is no longer blocked by that template.
- Individual sessions have capacity one and a database trigger binds every reservation or waitlist row to the configured `individual_client_id`. The configured client is immutable once set, API writes reject mismatched clients, and capacity remains one.
- Cancelling a session changes active reservations and waiting entries to `cancelled_by_center`, records prior/new states and actor in append-only audit, retains history, and blocks later attendance or cancellation changes. Cancelled sessions are terminal and cannot be reopened.
- Service/area archival rejects future scheduled sessions and future active templates in API and database guards. Booking and waitlist writes recheck current service and area status inside their transaction.
- Role matrix: Trainer and Admin can create/cancel sessions and templates, manage reservations and waitlist, correct attendance, and authorize over-capacity. The server keeps these as separate `reservations.manage`, `reservations.attendance` and `scheduling.override_capacity` grants. Reception/Management lacks attendance and override.
- Attendance/no-show can be reversed while a session is scheduled; each real state change audits previous/new status, actor and database timestamp.
- UI confirmations now cover reservation cancellation, session cancellation and over-capacity approval. Overbooking displays `Sobrecupo +N`. Individual appointments cannot silently become group sessions; client-bound sessions hide capacity and group booking controls. Client search is an accessible keyboard-operated combobox.
- Canary `Hoy`, responsive detail feedback, stable weekly rendering during mutations, human-readable failures, visible individual labels and readable seat/waitlist counts are included. The weekly API exposes only the non-PII `isIndividual` marker; `Cita individual` appears on the card and detail. Reopening appears only for `attended` or `no_show`, and capacity copy uses `1 libre` / `N libres`.
- Screenshots cover 1440/768/390 px plus free/full/waitlist/overbooked/individual/eligibility-blocked sessions, the three confirmation dialogs, and loading/error states. Evidence is in `docs/evidence/2J-030/`.
- The existing individual-session screenshot predates the weekly `isIndividual` contract and does not show “Cita individual”. UI tests verify the card and detail labels, but a fresh browser capture remains pending because the available browser control blocked navigation to the local development server.

## Runtime boundary and exclusions

The running configuration intentionally fails closed when the server cannot verify a client's plan right or available balance. Integration tests inject a server-owned eligible resolver. No balance is consumed, no entitlement is fabricated, and client identity continues to reference `clients.id` without copying client data into calendar rows.

Automatic waitlist promotion, penalties, cancellation windows, recurrence horizon/automation, push reminders, resources/rooms and full payment or entitlement consumption remain outside this task. Cancellation of a session by the centre has the explicit state/history behavior described above.
