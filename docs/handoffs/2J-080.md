## Behavior

Active recurring templates materialize missing sessions over the next 90 Canary calendar dates. Materialization runs when a single or batch template is created, before weekly calendar data is returned, and before the authenticated member session list (`GET /api/me/sessions`) is returned. The member route first validates the active client and query, then uses the same transaction-locked materializer; repeated reads are idempotent and do not expose template records. This keeps the rolling horizon fresh through normal member discovery even when staff have not opened Calendar. It respects weekday, `startsOn`, finite or open-ended `endsOn`, service/area/professional activity and the template's local time. Sessions use `Atlantic/Canary`, so wall-clock time remains stable across DST changes.

An advisory transaction lock serializes concurrent materializer runs. The existing unique `(template_id, starts_at)` invariant plus an immutable `template_occurrence_date` unique key and `ON CONFLICT DO NOTHING` make retries idempotent, including after an occurrence's time or date changes. Migration backfill assigns the immutable date to one existing row per template/date and preserves any pre-existing duplicate rows without deleting them; the materializer also detects legacy rows by their Canary local date. Existing generated sessions are never overwritten; cancelled and overridden occurrences remain durable. Archiving a template stops future generation without removing already materialized sessions.

`PATCH /api/calendar/sessions/:sessionId` edits only a scheduled concrete occurrence. It keeps the template provenance and existing reservations, checks active service/area and professional availability/conflicts, and rejects capacity below current occupancy. Payloads may include `overrideAvailability: true` and `availabilityReason` (3–240 trimmed characters); the reason is mandatory, `staff.schedule.override` is enforced server-side, and concrete-session conflicts or inactive professionals remain hard failures. Authorized Admin Calendar users see the explicit warning “Este cambio queda fuera del horario habitual del profesional.”, must confirm the exception and provide a reason, then save only that occurrence. The transaction writes both `session.occurrence_overridden` and `session.availability_override` audit events. Migrations `0025_calendar_occurrence_overrides.sql` and `0026_calendar_template_occurrence_identity.sql` add the audit action and immutable occurrence date; historical migrations were not changed.

Admin calendar no longer asks staff to generate each date. It explains automatic upcoming sessions, shows template details, and provides “Editar esta sesión” with a date-only scope, local Canary date/time, duration, trainer and capacity. The UI marks overridden occurrences.
