# 2J-098B-0 — Booking gate (refactor en modo sombra)

> Lee primero `docs/architecture/epics/2J-098-master.md` (secciones `BOOKING GATE`, `LEDGER MODEL`).

## Objective

Extraer un único **Booking Eligibility Gate** que sea la autoridad para crear reserva, unirse a la waitlist, promocionar desde la waitlist y previews. Debe poder devolver **varios motivos** y estar preparado para que A y E le añadan etapas. Es un refactor **sin cambio de comportamiento**, validado en modo sombra.

## Context

Hoy la elegibilidad está repartida entre `booking-eligibility.ts`, `calendar.ts` (`debtBlocksNewBooking`, `missingDocuments`, comprobaciones de capacidad), `client-app.ts` y la promoción de waitlist. Los códigos actuales (`overdue_balance_blocks_booking`, `required_documents_pending`…) los usan el Admin Web y la app Member.

## In scope

1. Módulo `booking-gate` con `evaluateBookingGate(tx, entrada)` y etapas en orden fijo: sesión → cliente → servicio/área → derecho → pago → documentos → conflicto de horario del cliente → capacidad. Las etapas "pago" y "selección de periodo" existen como **ganchos** que hoy devuelven el comportamiento legacy.
2. `intent`: `reserve | waitlist_join | waitlist_promote | preview`; conserva que `waitlist_join` ignora deuda y documentos.
3. Salida con `reasons[]` (`code`, `overridable`, `requiredPermission`, `details`), acumulando motivos.
4. Registro de códigos estable con alias de los códigos actuales durante una versión de API.
5. **Modo sombra:** flag `booking.gate.v2`; el gate nuevo se ejecuta junto al código actual, se comparan resultados y se registran divergencias; se sirve el resultado actual hasta cero divergencias.
6. Batería de **tests de caracterización** de todos los motivos y combinaciones actuales.

## Out of scope

Snapshot de política, motivos de cancelación, etapa de pago nueva, selección de periodo, cambios de comportamiento, cambios de UI, nuevos códigos de dominio salvo los ganchos.

## Dependencies

098-0 (reloj, utilidades de test).

## Domain invariants

- Para todo caso cubierto, el resultado del gate nuevo = el del código actual (mismo `allowed`, mismos motivos principales, mismo derecho elegido).
- El backend decide; el frontend solo muestra el motivo.
- La promoción reevalúa todo en la transacción y no se salta reglas.
- `waitlist_join` mantiene su comportamiento actual con deuda y documentos.

## Files likely affected

`apps/api/src/booking-eligibility.ts`, `apps/api/src/calendar.ts`, `apps/api/src/client-app.ts`, nuevo `apps/api/src/booking-gate/*`, tests de calendario y cliente.

## Migration

Ninguna.

## Feature flags

`booking.gate.v2` (apagado: se sirve el código actual; sombra: se compara; encendido solo tras cero divergencias y revisión).

## Tests

- Caracterización: sesión cancelada, iniciada, individual de otro cliente, cliente archivado, servicio/área archivados, sin derecho, servicio no permitido, derecho no iniciado/caducado/pausado/cancelado, cuota legacy `period_quota` agotada, bolsa `sessions_quota` agotada, deuda, documentos, conflicto de horario del cliente, sesión llena, sobrecupo autorizado, selección de derecho entre alternativas.
- Intents: `reserve`, `waitlist_join` (ignora deuda/documentos), `waitlist_promote`, `preview`.
- Acumulación de varios motivos a la vez.
- Modo sombra: cero divergencias en toda la batería.

## Manual acceptance

Reservar, cancelar y unirse a la lista de espera desde Member y Admin como antes; los mensajes de bloqueo no cambian.

## Risks

Regresión sutil por cambio de orden de etapas → batería de caracterización + sombra antes de servir.

## Definition of Done

Batería completa verde; flag en sombra sin divergencias documentadas; nada cambia para el usuario; revisión de SHA exacto; handoff actualizado.

## Handoff requirements

`docs/handoffs/2J-098B-0.md`: mapa antiguo→nuevo de códigos, resultados del modo sombra, ganchos disponibles para A-1 y E-3, cifras de validación.
