# 2J-077 — Notificaciones y automatización operativa V1

Status: implementation in review; Draft PR from `agent/codex/2J-077-notifications-automation`, based on the merged 2J-076 head `5ae43a93cc1313d98ae3618524269996cf1a7238`. Do not merge until independent backend/security and UX review.

## Delivered in this slice

- Additive migration `0020_notifications_outbox.sql` creates a durable versioned domain-event outbox, in-app inbox, center-level reminder settings, retry/dead-letter fields and dedupe constraints. No provider credentials, tokens, message bodies or health data are stored in the notification payload.
- Booking creation (including individual sessions), cancellation, waitlist entry/promotion, and center/client messages append events inside the existing PostgreSQL transaction. An aborted domain transaction therefore leaves no notification event; replays do not emit duplicates.
- A standalone `pnpm --filter @2j/api notifications:worker` process persists in-app deliveries, uses `FOR UPDATE SKIP LOCKED`, exponential retry and dead-letter after eight attempts. It also schedules booking reminders, plan-expiry notices, low-session-balance notices and pending-document reminders. Reminder due times use absolute instants; date-based expiry reads `Atlantic/Canary`.
- Client and Staff apps provide unread counts, inbox pagination, mark-one/read-all and empty states. API access is bound to the resolved client id or staff actor id; pagination and mutations are recipient-scoped. Admin Web exposes simple notification preferences behind `settings.manage`.
- Staff message fan-out only targets active staff whose role grants `communication.read`; the saved notification contains generic copy and no message text or client identity. The notification list does not expose finance, cash, health or other-client data.

## Intentionally not live / pending production

- Push and email have no provider adapter, tokens, credentials, endpoint, or delivery path. In-app delivery is the only active channel.
- Rules for fiscal/debt notifications, richer staff timeclock reminders, marketing, campaigns, SMS/WhatsApp, and a configurable automation builder remain out of scope. No production push provider or subscription should be selected without Juanjo's approval.
- A deployment must run the API and the durable worker as separate managed services with the same PostgreSQL database and graceful restart monitoring. Do not use workstation cron, a desktop process, Redis, or BullMQ.
- Client message notifications target `/messages`; confirm that route resolves to the client conversation surface in the deployed client app before enabling production messaging notification links.
- The worker scans upcoming bookings 90 days ahead to persist reminder jobs; this is an internal scheduling lookahead, not a recurring-session generation horizon.
