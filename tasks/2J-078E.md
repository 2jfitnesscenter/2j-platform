# TASK 2J-078E — Platform ↔ Training verified proof bridge

## Goal

Connect the existing Platform 078C internal `TrainingLinkVerifier` boundary to Training's 078D `/api/platform/v1/link-proofs/exchange` endpoint. A strict `{v:1, code}` assertion contributes only the opaque Training proof code. Platform supplies transaction/person/audience/purpose/challenge digest from its durable context, signs the exact serialized request with the existing 2J-SERVICE-AUTH-V1 canonicalizer, and accepts only a strict response whose full context matches.

## Scope

- Add a real outbound Platform verifier factory with HTTPS/origin-only URL validation, exact fixed path, redirects rejected, bounded JSON, strict response schema, freshness-safe signature metadata, abort/timeout handling, and fail-closed transport/error behavior.
- Reuse `buildTrainingServiceAuthHeaders` and `canonicalizeTrainingServiceRequest`; do not add a second canonicalization contract.
- Wire the verifier into the existing internal transaction service. Both `trainingVerifiedLinkingEnabled` and `trainingServiceCallsEnabled` must be true, and valid runtime service configuration must exist, before the verifier can make a request.
- Add the 078D shared golden vector, end-to-end signed mock HTTP receiver test, response/transport/binding negative tests, and config/flag no-traffic tests.
- Do not add a public verify endpoint, database migration, Training repository change, or production credential.

## Config

`TRAINING_SERVICE_BASE_URL`, `TRAINING_SERVICE_KEY_ID`, and `TRAINING_SERVICE_SECRET` are runtime-only adapter configuration. The secret is canonical base64url with at least 32 decoded bytes. These values do not activate outbound calls. The existing `trainingVerifiedLinkingEnabled` and `trainingServiceCallsEnabled` server options remain independent, default false, and are not set from environment by the production entrypoint.

## Protocol behavior

Request body field order is fixed: `v`, `code`, `transactionId`, `personId`, `audience`, `purpose`, `challengeDigest`. The path is always `/api/platform/v1/link-proofs/exchange`; the service request gets a fresh UUID independent from the transaction ID. Responses are capped at 16 KiB, require `application/json`, reject invalid UTF-8/JSON and extra fields, and must match all context fields exactly. Only `trainingUserId` is returned to the existing verifier protocol for its atomic `pending → verified` transition.

All unsuccessful remote outcomes return a proof-rejected internal result or the existing verifier-timeout result. Neither changes the pending transaction nor persists a Training subject. No Training error body is forwarded to public routes.

## Deliberately out of scope

Canonical `personId` ↔ `trainingUserId` link, remote ACK/lifecycle, SSO, central passkey, redirect/UI, production keys, LIVE activation, automatic retry/reconciliation, Training code changes, and dependency upgrades.

`remote proof verified != canonical Training link active`

`Training proof consumed but Platform response lost remains unresolved until lifecycle/reconciliation phase`

## Risks to keep visible

Training can consume the one-time proof but Platform may lose the HTTP response. Platform then remains pending, while a retry receives `proof_already_consumed`. This remains unresolved until a separately designed lifecycle/reconciliation phase; do not retry aggressively or create a canonical link to mask it.

Training 078D pre-go-live follow-ups remain external dependencies: proof supersede matching is narrow, disabled-account proof may become usable after re-enable, issuance rate limiting and fsync durability are absent, and file-store concurrency is single-process only. This task does not change Training.
