# 2J-089 — Platform ↔ Búnker contract V1

## Outcome

Connect the canonical Platform identity link to a small, read-only Training summary. Platform owns the person-to-Training link; Training keeps its own user identity and all training records. The databases remain separate.

## Reused foundation

Reuse the verified link lifecycle from 2J-078B/C/E/F-B and the existing `2J-SERVICE-AUTH-V1` signer, verifier, key rotation, freshness window, and persisted replay store. Only `training_account_links.status='active'` for an active Platform person is eligible. Pending, revoked, conflicted, or otherwise unavailable links never trigger a Training lookup. No email, phone, name, browser session, or client-supplied Training ID participates in resolution.

## Contract

Platform sends a signed read-only query to Training at the fixed path `POST /api/platform/v1/training-summary` with `{ "v": 1, "trainingUserId": "..." }`. Keeping the opaque ID in the bounded signed body avoids placing a durable identifier in a URL. Training accepts only the exact static path and request body, checks service auth and replay protection, then reads the named active Training account.

Training success response:

```json
{
  "v": 1,
  "trainingUserId": "opaque-training-id",
  "trainingStatus": "active",
  "asOf": "2026-10-13T12:00:00.000Z",
  "currentProgram": { "id": "program-id", "name": "Fuerza base" },
  "recentActivity": { "lastTrainingAt": "2026-10-12", "sessionsLast30Days": 4 }
}
```

`currentProgram` is optional. `recentActivity` is a bounded aggregate, not workout history. Training returns only these fields; it excludes exercise logs, performance/RM data, body or health metrics, trainer notes, nutrition notes, permissions, and settings. Platform validates a strict schema and exact returned Training ID before exposing a member-safe projection that omits both Training and program IDs.

The Member API returns exactly one of:

- `{ "status": "not_linked" }` for missing, inactive, pending, revoked, or non-active links;
- `{ "status": "linked", "summaryStatus": "available", "summary": { ... } }` for an active link and valid response;
- `{ "status": "linked", "summaryStatus": "unavailable" }` when the active link exists but Training is disabled, missing, slow, malformed, or unauthenticated.

Training 404 for an unknown/disabled account is intentionally mapped by Platform to the generic unavailable state. Profile remains independent of Training availability. Both member and internal responses use `Cache-Control: no-store`. Failures expose no internal URL, stack trace, signature, key, or remote payload.

## Configuration and rollout

No credentials are committed or requested by this task. Platform calls require both `TRAINING_SERVICE_CALLS_ENABLED=true` and `TRAINING_SUMMARY_ENABLED=true`, an exact `TRAINING_SERVICE_ALLOWED_ORIGINS` allowlist, the configured Training base URL, and the already-established service key ID/secret. Training independently requires `PLATFORM_TRAINING_SUMMARY_ENABLED=true` and the existing `PLATFORM_SERVICE_AUTH_KEYS` allowlist. Every flag defaults off. Missing or invalid configuration fails closed.

The Búnker tab displays only real link/summary status when a Member session requests it. Preview remains fixture-only and does not invent a link. Its launch target remains the existing Training app. No SSO, entitlement matrix, browser token exchange, or synchronization is included.

## Ownership

| Data | Owner |
| --- | --- |
| `personId`, client/staff facets, link lifecycle and revocation | Platform |
| `trainingUserId`, routines, progression, workouts, and Training profile | Training |
| Member-visible common shell and member-safe summary projection | Platform |

## Acceptance and validation

- Only an active canonical link reaches Training; request input from the browser cannot select a remote identity.
- Training authorizes only exact signed Platform service requests; timestamp freshness and durable request replay protection reuse the existing service-auth system.
- Disabled/missing Training accounts, timeouts, bad signatures, malformed responses, and inactive links fail closed without taking down Profile.
- Separate test coverage in both repos enforces the same semantic V1 response contract.
- Both PRs remain Draft and cross-reference one another. Neither is merged independently.

Both repositories include the same versioned fixture at `contracts/2J-089-training-summary-v1.json`. Their tests load that fixture directly; Training's response test separately confirms runtime-derived activity values. No cross-repository shared package was added.
