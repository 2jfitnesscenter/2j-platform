# 2J-020 — Clientes 360, primera entrega

Priority: P1 · Risk: high · Status: IMPLEMENTATION

## Objective

Ship a real PostgreSQL-backed client directory with server-authorized search and a 360 profile. The first slice owns only basic identity/contact data, active/archive state and its own create/archive history; connected modules keep their existing sources of truth.

## Product rules

- All trainers can read all clients. Reception/Management can read client records. Admin retains the approved wildcard.
- Health, billing, training and administrative permissions remain independent. Do not infer health or financial fields from a client profile.
- The 360 page must expose these sections: Summary, Reservations, Payments, Training, Progress, Health, Docs/Forms, Messages and History.
- Training/Búnker/Health remain in 2J Fitness App. Do not copy their data or implement a parallel assignment, health or progression model.
- No full payments, calendar, reservations, waitlist, adherence/risk formula, health detail, document contents, messaging or onboarding automation in this task.
- No leads, birth date, clinical data, payment data, documents or custom-field builder in this slice.

## Scope

- PostgreSQL migration and Drizzle schema for a minimal client profile and append-only create/archive events.
- Server-authorized directory/search, detail, create and archive endpoints; archive preserves the profile and history.
- Responsive premium directory and 360 profile with all nine sections. Only Summary and this module's History contain data in this slice; other allowed sections explain their source and show an honest not-connected state.
- Deny PII routes by default. Never authorize from role headers, query parameters, body fields or browser visibility. Add `Cache-Control: no-store`; exclude search terms and contact fields from logs/audit.
- A fixed server-side demo role is allowed only in `NODE_ENV=development` on the loopback-only API; production has no demo identity. It is not an identity provider.
- Until action-level write grants are decided, `clients.manage` is Admin-only. Do not infer write permission for Trainer, Reception/Management or Accountant.

## Acceptance

- Search matches name, email and phone without placing the search term in request logs; result and detail endpoints return no PII without server-resolved `clients.read`.
- Unknown/missing session context returns 401; unauthorized roles return 403; caller-supplied role headers have no effect.
- Admin can create and archive a client; other roles do not receive write access. Archive never deletes client/history records.
- Profile includes the nine named sections, displays only client-owned data, clearly marks disconnected modules, and does not copy training/Health records.
- Sensitive sections have no backing data endpoint in this slice; future section APIs must add server-side permissions before returning records.
- Database constraints, integration tests with PostgreSQL, permission tests, UI behavior tests, typecheck, build, audit and secret scan pass.

## Decisions still gated

- Exact client write grants for Trainer and Reception/Management.
- Production identity/session provider and credential transport.
- Health field/purpose scopes; accountant scopes; document/consent permissions and retention.
- Data displayed from plans, payments, scheduling, training and Health; adherence and alert formula.
