# 2J-098C-1 — Motor RBAC granular, esquema y UI Admin

> Lee primero `docs/architecture/epics/2J-098-master.md` (sección `RBAC MODEL`; decisiones R-01…R-05).

## Objective

Construir el motor de permisos con **permiso + alcance**, concesiones/denegaciones, plantillas, asignación explícita de clientes a Trainers y la UI Admin para configurarlo, sin cambiar el comportamiento actual.

## Context

El RBAC actual es un mapa fijo por rol (F-13). No existe autenticación real de staff (F-9): este PR se construye y prueba con el resolver actual y **no se activa en producción**.

## In scope

1. Registro de permisos con metadatos (extiende 098-0): `domain`, `sensitive`, `delegable`, `dependsOn`, alcances admitidos. Clasificación de no delegables según R-03; el servidor rechaza concederlos a Trainer.
2. Tablas: `staff_permission_policies`, `staff_policy_entries` (permiso, efecto `grant|deny`, alcance), `staff_actor_policies` (principal `actor_id`, política, quién y cuándo) y versión de política por actor.
3. `client_trainer_assignments` (`client_id`, `professional_id`, `role` `primary|secondary`, `assigned_by`, `assigned_at`, `ended_at`): como máximo un principal activo por cliente, secundarios ilimitados. Permiso para asignar clientes.
4. Motor de evaluación: efectivo = rol base ∪ plantilla ∪ concesiones del actor, menos denegaciones; deny gana; alcance más amplio entre concesiones salvo deny. Plantillas **copiadas** al asignar. Plantillas de sistema sembradas desde el mapa estático (Trainer = comportamiento actual exacto).
5. Contexto de autorización ampliado y `scopeOf(ctx, permiso)`; constructores de predicado SQL por recurso (`all`, `own`, `assigned`); doble lectura con el mapa estático cuando no hay política.
6. API: gestión de políticas/plantillas/asignaciones y `GET /api/session/capabilities` ampliado (permisos efectivos con alcance).
7. UI Admin (Equipo → persona → Permisos): rol base, plantilla, matriz por dominio con interruptor y alcance, vista "qué puede hacer ahora", aviso de riesgo, confirmación en cambios críticos, y asignación de clientes a Trainer.
8. Auditoría de cambios (diff antes/después, actor, motivo) en `platform_domain_audit_events` (dominio `rbac`).

## Out of scope

Aplicar alcances a las rutas de calendario/clientes/economía/tienda (C-2); activar en producción; proveedor de identidad.

## Dependencies

098-0.

## Domain invariants

- Sin configuración granular, el comportamiento = el actual (golden de 098-0 intacto).
- Deny siempre gana.
- Los no delegables no se conceden a Trainer; no se puede quitar al último Admin ni auto-escalar.
- `own` sin profesional vinculado → sin acceso (falla cerrado). `assigned` solo con asignación explícita activa (no se deriva de reservas ni clases).
- Un cambio de permisos se aplica en la siguiente petición.
- La UI refleja capacidades; nunca es autoridad.

## Files likely affected

`packages/permissions/*`, `apps/api/src/` (autorización, nuevo módulo `rbac`), `apps/api/migrations/`, `apps/api/src/schema.ts`, `apps/admin-web/src/` (Equipo/Permisos), tests.

## Migration

Tablas nuevas + siembra de plantillas de sistema. Sin cambiar datos existentes.

## Feature flags

`rbac.granular.enabled` (apagado; no se enciende en producción sin autenticación real de staff).

## Tests

- Golden de los 4 roles sin política; matriz permiso × alcance × política; deny gana incluso con concesión posterior.
- No delegables rechazados; último Admin protegido.
- Cambio de permisos en caliente entre dos peticiones.
- Asignación de clientes: principal único, secundarios, fin de asignación.
- Auditoría completa de cambios; plantillas copiadas (editar plantilla no cambia a quienes ya la tienen).

## Manual acceptance

El propietario crea una política para un Trainer de prueba, ve el resumen "qué puede hacer", asigna clientes y comprueba que la UI muestra las capacidades devueltas.

## Risks

Fuga por mala evaluación de alcance en C-2 (aquí solo el motor); bloqueo del propio Admin; UI de permisos demasiado técnica → validar con el propietario.

## Definition of Done

Motor y UI funcionando con flag apagado; golden intacto; migración probada; revisión de SHA exacto; aceptación visual; handoff.

## Handoff requirements

`docs/handoffs/2J-098C-1.md`: registro completo de permisos con clasificación, esquema final, contrato de capacidades, guía para C-2.
