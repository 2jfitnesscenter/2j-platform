## Arquitectura

`apps/client-app` es una app ligera React + TypeScript + Vite. Consume una fachada cliente y las rutas existentes de portal de formularios/consentimientos. No llama a endpoints de calendario staff ni envía un ID de cliente. Capacitor Core, Android, iOS y CLI están declarados; `capacitor.config.ts` prepara `com.2jfitness.client`, y la salida web es `dist`. No se han generado proyectos nativos ni publicado artefactos en tiendas.

El manifiesto permite instalar la PWA. El service worker cachea exclusivamente shell/recursos estáticos; ignora `/api/*`, no mantiene una cola offline y no confirma mutaciones sin respuesta del servidor. Safe areas y navegación inferior se adaptan a móvil. La API debe estar en el mismo origen para web; `VITE_API_PROXY` configura el proxy local de Vite. Capacitor admite una URL absoluta con `VITE_API_BASE_URL`; el origen HTTPS y CORS nativos deben definirse al conectar autenticación central.

## Identidad y autenticación

`clientAuthorizationResolver` es la única fuente autorizada del `clientId`. La fachada vuelve a comprobar que el cliente sigue activo; no acepta `clientId` en query o body para lecturas propias. En el runtime sin resolver configurado, las rutas de cliente responden 401.

Para demo local únicamente, el servidor permite `LOCAL_DEMO_CLIENT_ID` cuando `NODE_ENV=development`; `HOST` sigue limitado a loopback y no se crea contraseña compartida. La plataforma aún no tiene el flujo real de sesión de cliente integrado aquí: antes de producción hay que conectar el resolver a la identidad central, habilitar logout/session expiry y definir la URL HTTPS/API y CORS de la app nativa. No almacenar credenciales en la app.

## API de App Cliente

- `GET /api/me`: perfil propio mínimo.
- `GET /api/me/membership`: asignaciones y derechos efectivos para presentación; no calcula decisiones de reserva.
- `GET /api/me/bookings`: reservas e historial propios, más estados de waitlist propios.
- `GET /api/me/bookings/:id/cancellation-preview`: comprueba propiedad y obtiene preview desde la misma política de servicio.
- `GET /api/me/sessions?from=YYYY-MM-DD&to=YYYY-MM-DD`: agenda publicable con servicio, área, entrenador visible, ocupación/lista de espera y solo el estado propio; rango limitado a 31 días.
- `GET /api/me/sessions/:id`: detalle y elegibilidad resuelta por `createBookingEligibilityResolver`.
- `POST /api/me/sessions/:id/reservations`, `POST /api/me/sessions/:id/waitlist`, `PATCH /api/me/bookings/:id/cancel`, `PATCH /api/me/waitlist/:id/cancel`: aliases self-service del mismo motor de 2J-074. Las rutas preservan transacciones, locks, consumo/restauración, promoción, auditoría e idempotencia existentes; no reimplementan reglas.
- Las rutas de portal ya existentes `/api/client-portal/form-assignments`, `/api/client-portal/consents` y sus mutaciones también derivan titular del resolver cliente. La app no expone datos de terceros.

La cancelación exige preview previo y confirmación. La salida de waitlist conserva la semántica central. Los errores de elegibilidad se traducen a texto humano.

## Experiencia implementada

Navegación fija de cuatro destinos: Inicio, Reservar, Mis reservas y Perfil. La Home muestra próxima reserva, plan/bono y balance derivado. Reservar presenta días seleccionables dentro de semanas navegables, plazas, entrenador visible, cita individual y estado de la reserva propia. El detalle consulta elegibilidad central, permite elegir explícitamente entre varios derechos y ofrece reserva o waitlist. Mis reservas separa próximas, espera e historial; Perfil muestra la información propia y sus asignaciones. También permite completar formularios asignados y aceptar consentimientos publicados con acción explícita. El módulo Training solo se señala cuando la asignación contiene acceso; no se abre ni duplica Búnker.

## Privacidad

Pruebas PostgreSQL verifican que A solo recibe su perfil y sus reservas, que el body con ID ajeno es rechazado, que B no puede cancelar ni previsualizar una reserva de A ni salir de su waitlist, y que un cliente anónimo falla cerrado. El listado publicable no consulta datos de nombres/email de otros clientes. Mutaciones llevan el actor auditado como cliente derivado del resolver.

## FUTURA INTEGRACIÓN BÚNKER

La app mantiene una identidad `clients.id` central. Una asignación puede incluir `plan_module_accesses.module='training'` y capabilities del namespace `training.*`; 2J-075 puede presentar el acceso, pero no crea perfiles, sesiones, historial ni datos de salud en otra base. Una integración posterior resolverá el mismo `clientId` con Platform y abrirá la experiencia de Búnker existente; no se copiarán medidas, rutinas ni Health. No se modifica `2jfitnessapp` en esta TASK.
