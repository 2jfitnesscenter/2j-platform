## Delivered boundary

The local Member pilot uses the existing central identity chain: an active `platform-pilot` auth subject resolves to its immutable `personId`, then to the active `platform_person_clients` facet, then to an active client. The resolver returns only `{ clientId }` to the existing `/api/me/*` and client-portal handlers. Browser query parameters, request bodies and headers never select the member. There is no email matching, Training identity change, or shared cookie.

`POST /api/pilot/member/login` verifies a seeded synthetic code by SHA-256 hash, then creates a fresh 256-bit random bearer value. PostgreSQL stores only its SHA-256 digest, person and subject IDs, creation/expiry/last-seen timestamps and revocation timestamp. The eight-hour host-only cookie is `HttpOnly; Path=/; SameSite=Lax`; `Secure` is added for HTTPS. Login revokes the presented active session before issuing a new one. Logout revokes the session and expires the cookie. Session creation/revocation is captured in append-only audit rows without storing the bearer value or credential.

Unsafe `/api/me/*` and `/api/client-portal/*` requests require an exact configured `Origin`, or a matching `Referer` when Origin is absent. The pilot API additionally requires a loopback host and is enabled only by `PILOT_MEMBER_AUTH_ENABLED=true` plus an exact loopback `MEMBER_APP_ORIGIN` in development/test. Missing configuration leaves the pilot endpoints disabled; requesting enablement under another `NODE_ENV` fails at startup.

The Member app exposes the local code form only with `VITE_2J_PILOT_MEMBER_LOGIN=true` and only outside fixture preview. Preview behavior remains gated by the existing build flag plus exactly one `preview=1`, and still makes no API calls. The launcher now starts a dedicated Member API, opens its normal URL without `preview=1`, and retains the preview opt-in URL.
