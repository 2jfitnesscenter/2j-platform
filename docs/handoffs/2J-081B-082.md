## Review delta — visual schedule editor and plan tariff catalog

The reviewed starting head for this bounded delta was `19923faabc2bc7a411d3ca0b72be96176b93a717`. “Configurar horarios” now opens a Monday–Sunday, 06:00–22:00 timetable. Clicking a free cell adds a draft recurring block at that local time and day; clicking the same time on another day adds that day to the repeated schedule. Service color is the stable existing hash/token mapping. Service, professional, duration, capacity, and validity dates remain editable, and the preview summarizes days, times, capacity, and date range. Saving continues to call `/api/calendar/templates/batch`; visual Monday-first indices are translated to the API’s Sunday-zero weekdays. Existing templates render in the grid and can be archived through the existing confirmation/API. Materialization, Canary handling, overrides, and cancellation semantics were not changed.

“Servicios y planes” now keeps the actual service list as the left-side selector and presents the selected service’s tariffs in a compact table, switching to cards on narrow screens. The table shows name, product type, quota, renewal period, base PVP, state, included services, and actions. Expandable details retain rights, module access, version and new-version actions; draft activation remains available. IGIC and a separate in-app price are omitted because the product model has no such fields.

The birthday summary labels its second count “Semana visible”. `/api/calendar/week` returns the separate “today” count only for client managers; navigating to another week changes the visible-week count without changing the actual Canary-today count.

## Implementation detail

- Calendar collisions use interval grouping; touching boundaries are not overlaps. Crowded groups scroll horizontally with keyboard access and a readable card minimum width.
- Service color is a deterministic hash of the service UUID into the existing semantic 2J color tokens; it is stable across reloads and does not persist product metadata.
- `clients.birth_date` is nullable. Birthday data is returned only to actors with `clients.manage`, as a minimal name/date read model. Admin profile edits are audited and email uniqueness rules remain enforced.
- Catalog mutations require `catalog.pricing.manage`; Admin is allowed, Trainer/Reception/Accountant are denied, and catalog reads remain available under their existing permissions.
- Draft plans expose “Activar plan”; the existing activation endpoint remains authoritative and UI refreshes from its response.
- The Staff search capability no longer overwrites `reservationManage`. After a successful booking the selected session’s occupancy/waitlist counts are recomputed from the server attendee response.
