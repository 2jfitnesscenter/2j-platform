# Handoff — 2J-079A 2J Hub Client Preview

## Outcome

Added the 2J Hub surface to `apps/client-app` as an additional member entry point. It has five primary destinations (Inicio, Reservar, Entrenar, Centro, Perfil), a header notification bell, and a separate internal-only pilot panel. Training remains a direct external handoff to `https://app.2jfitnesscenter.com`; there is no iframe, SSO, shared cookie, or write to Training.

Fixture preview is activated only when the build flag `VITE_2J_HUB_PREVIEW=true` is present and the URL explicitly contains one `preview=1` parameter. A missing parameter, any other value, or duplicate `preview` parameters keep the app in normal API mode. It uses fictional profile, membership, reservation, notice, form and consent data; the client returns before API access in this mode and disables writes. Normal mode continues to call the existing member API routes and does not fake a successful result. Server-side authorization remains responsible for access to PII and operations.

## Explicit pilot status (addendum A–H)

**A. Member experience today:** Yes for the navigable fixture preview. The existing API-backed member experience can be tested locally only when a valid client session/identity is supplied. There is no production member identity/session integration in this repository today, so a real member pilot cannot be hosted safely yet.

**B. Trainer/staff today:** The existing `apps/staff-app` can be inspected locally against a synthetic development database and the API's development-only `LOCAL_DEMO_ROLE=trainer`. It is linked separately from the Hub's internal pilot panel. This is a local demo role, not real staff authentication and not safe for public hosting.

**C. Admin today:** The existing `apps/admin-web` can be inspected locally against a synthetic development database and `LOCAL_DEMO_ROLE=admin`. The admin README explicitly states there is no production sign-in; keep it loopback-only. It is linked separately and is not embedded in the member Hub.

**D. Real Platform data:** In normal member mode, the Hub reads `/api/me`, membership, bookings, sessions, form assignments, consents, and notifications, and uses the existing corresponding API mutations. Those routes are API-backed, not mocked. Current standalone API runtime lacks an approved production identity/session provider, and the reservation eligibility resolver fails closed when rights cannot be verified. Therefore these routes are not a live hosted pilot today.

**E. Fixture-only data:** The gated preview uses clearly labelled fictional data for Inicio, membership, reservations, sessions, notice, forms and consent. Reserve/waitlist, cancellation, form submission, consent acceptance, and notification changes do not write; the preview reports that actions are disabled or simulated locally. Screenshots/demos should use this mode only.

**F. Impact on existing `2jfitnessapp` users:** **None.** This change does not touch the Training repository, routes, login, sessions, cookies, passkeys, Búnker, workouts, Health, routines, Training Coach, users, or production configuration.

**G. Can `app.2jfitnesscenter.com` continue exactly as before?** **Yes.** Training remains independently reachable through the visible Entrenar handoff, and the Hub does not control or modify it.

**H. What remains to expose `inicio.2jfitnesscenter.com`?** Before DNS/proxy/TLS changes, the owner must approve a real deployment. Technical prerequisites are: (1) an approved production identity/session integration and server-side authorization for member PII/actions; (2) production API/database hosting, network policy, CORS/origin and secure session configuration; (3) a reviewed Hub build with preview fixtures and pilot links disabled; (4) static hosting with SPA fallback and secure same-origin/API routing; (5) DNS record for `inicio.2jfitnesscenter.com`, TLS certificate, and reverse-proxy/CDN routing; and (6) operational monitoring, rollback, backups and an explicit owner-only allowlist/invitation gate for the first pilot. None of those infrastructure changes were performed. Admin and staff must remain on separate authenticated URLs/surfaces; do not publish their current local demo endpoints.

## Local access

From the repository root, install dependencies and use the existing documented disposable PostgreSQL setup. For a visual-only member preview, no API or database is needed:

```powershell
pnpm install --frozen-lockfile
$env:VITE_2J_HUB_PREVIEW='true'
$env:VITE_2J_STAFF_URL='http://127.0.0.1:5175'
$env:VITE_2J_ADMIN_URL='http://127.0.0.1:5174'
pnpm --filter @2j/client-app dev -- --host 127.0.0.1 --port 5173
```

Open `http://127.0.0.1:5173/?preview=1`. Preview data is fictional, and no API requests are made. The actual local browser used for this handoff selected port 5180 because port 5173 was already occupied.

To inspect existing staff/admin apps, start them on loopback using the ports above and the repo README's disposable `2j_demo` database procedure. The API supports only one `LOCAL_DEMO_ROLE` at a time; restart it with `trainer` or `admin` to inspect the corresponding role. This remains development-only and must not be interpreted as real identity or a live pilot.
