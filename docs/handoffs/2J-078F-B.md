## Implemented

- Added migration `0024_training_canonical_link_lifecycle.sql`. Existing `explicit_admin` active/revoked rows retain IDs, user/person identity, versions, and explicit admin revocation semantics. Canonical states are `pending`, `active`, `revocation_pending`, `revoked`, and `conflict`; verified-proof rows must be created as pending with version 1 and immutable transaction/receipt references. Partial unique indexes reserve at most one nonterminal link per person and per Training user.
- Added `createRemoteTrainingReceiptReconciler()` for the fixed signed POST path, fresh request IDs, shared 2J-SERVICE-AUTH-V1 canonicalization, bounded strict JSON, HTTPS/origin validation, no redirects, timeout, and exact response schema/context validation.
- Added internal `createTrainingCanonicalLinkLifecycle()` and attached it to the Fastify app as an internal service only. It revalidates person/auth binding after the remote call, atomically recovers a pending transaction, then creates/replays a source-bound canonical pending link. No HTTP route was added.
- Historical `verifiedAt` is required to be canonical UTC, within original `createdAt..expiresAt`, and no more than 30 seconds ahead of the Platform clock. A transaction that is still pending after wall-clock expiry can be recovered; once durably cancelled/expired it cannot.
- Added safe audit actions for recovery, pending creation, and actual identity collisions. Audit payloads omit Training user ID and receipt/proof data.
- Independent `trainingCanonicalLinkingEnabled` flag defaults off and requires both existing verified-linking and service-call gates. No environment variable enables a gate.

## State transitions

| Entity | Allowed in this TASK |
| --- | --- |
| Proof transaction | pending → verified (normal proof or valid durable receipt recovery); verified → consumed/expired/cancelled under existing rules |
| Verified-proof canonical link | insert as pending v1 only; pending → active is rejected by the database |
| Legacy explicit-admin link | existing active row remains active; active → revoked remains supported and increments version |
| Future structural lifecycle | active → revocation_pending → revoked and conflict states are represented, but no remote lifecycle route/orchestration is added |
