# 2J-006 — Domain model and backend architecture

Priority: P0 · Risk: high · Status: REVIEW

## Objective
Turn the approved `TECH_ARCHITECTURE.md` direction into concrete, testable domain module boundaries and backend conventions before product behavior is implemented.

## Scope
- Modular TypeScript/Fastify backend boundary; PostgreSQL as transaction source of truth and Drizzle as persistence detail.
- Module dependency allowlist, single-use-case transaction ownership, explicit cross-module coordination, and post-commit outbox effects.
- Infrastructure-neutral domain package interfaces and tests for module graph/transaction policy.
- No production app change, server, migrations, business rules, auth, payments, or infrastructure credentials.

## Acceptance
- Every module in the approved architecture exists once in the machine-readable map; edges reference valid modules and form an acyclic graph.
- Domain contracts have no framework/database dependency.
- Transaction and side-effect policies are explicit and tests verify the architectural invariants.
- No pending product/legal decisions are silently resolved; decision gates are recorded.
- Typecheck, tests, build, security audit and independent review/QA pass before merge.
