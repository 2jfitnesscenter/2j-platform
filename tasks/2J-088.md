# 2J-088 — Member Profile V2

## Goal

Build one Member-facing Profile shell from real Platform-owned data while keeping each bounded system as owner of its own records. This task is read-focused; it adds no profile write API, purchase backend, Training integration, signature flow, or new authentication behavior.

## Profile sections

1. **Mi perfil** — current self-scoped name, email, phone, and account status.
2. **Cuotas y saldo** — active assignments, validity, and session balances already derived by the membership API. If there is no active assignment, the account and Profile remain available and the Member sees “No tienes ninguna cuota activa.” Other assignments remain visible under “Otras cuotas”. No monetary debt is shown because no self-scoped economic balance API exists.
3. **Mis servicios** — names and statuses come from the configured service referenced by an explicit right on an active assignment. The client does not hardcode service entitlements or infer access from labels.
4. **Tickets y compras** — restrained empty state until a real Member purchase-history API exists.
5. **Buzón** — opens the existing self-scoped notification view and shows its unread count. Center News remains separate and is described as appearing on Inicio.
6. **Contratos y certificados** — reuses current self-scoped form assignment and consent APIs, grouped into pending and completed/submitted states. Consent wording reports the recorded acceptance state and makes no legal-signature claim.

## Ownership and composition boundary

Platform owns the client facet, plan assignments, entitlement balances, service catalog, notification records, form assignments/responses, and consent acceptances. Profile composes those existing read models at the client boundary; it does not copy them into a new profile table. The membership response now adds the configured service name/status beside each referenced service id, without changing the source of truth.

Training remains the owner of training identity/profile, goals, training history, progression, body metrics, and coach assignment. A future visible Profile may compose those through an explicit person-scoped integration contract, but this task makes no Training request, creates no mirror table, and renders no placeholder Training card.

## Deliberate limits

- No edit path unless an existing Platform-supported path is already available; this task adds none.
- No Store, order, ticket, or purchase ledger.
- No self-scoped monetary debt display without an existing suitable API.
- No digital signature, profile photo, social feature, Training API, or Training synchronization.
- Preview data is fictional and stays zero-API, including Profile.

## Acceptance coverage

- Profile structure, active assignment and explicit service-right display.
- No-fee Member retains Profile, account information, inbox and documents access.
- Pending and submitted form state, consent acceptance state, and inbox unread summary.
- Purchase empty state and responsive card layout.
- Existing self-scoped API tests continue to verify identity comes from the server; query input cannot select another client.
- Preview profile uses only fixture data and never calls the API.
- Existing Inicio, booking, Búnker, Tienda, Ajustes, News, notification, Admin, and Staff flows remain in regression gates.
