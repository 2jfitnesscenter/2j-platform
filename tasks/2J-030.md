# 2J-030 — Calendario, Reservas y Lista de espera

**PR:** `2jfitnesscenter/2j-platform#8`  
**Branch:** `agent/codex/2J-030-calendar-bookings-waitlist`  
**Status:** implementation complete; independent review required; do not merge before review.

## Accepted scope

- Main screen is a weekly calendar using `Atlantic/Canary` time.
- Recurring templates and dated calendar sessions are distinct records. Generating a template occurrence requires an explicit date; no horizon or automatic generation is assumed.
- Active services and areas from 2J-010 configure sessions. V1 does not add rooms/resources.
- Staff can create a punctual group session or an individual session tied to an existing `client_id`.
- Staff can reserve a client, cancel a reservation, mark attendance or no-show, and add/remove a full-session waitlist entry.
- The roster and the Clients 360 Reservations section read the same reservation records through `client_id`; client names are joined at read time and never copied to calendar records.
- Staff with `scheduling.override_capacity` and Admin may overbook. Every overbook is separately audited.
- Permissions are checked server-side. Calendar reads, reservation management, client PII, and capacity override are distinct capabilities.
- Booking eligibility is a server-side `BookingEligibilityResolver` contract. It receives the transaction, client, service, and session start, and returns a server-verified entitlement reference. Default wiring fails closed until client-plan assignments and available balances exist. This task does not consume or mutate financial balances.

## Explicitly excluded / pending product decisions

- Automatic waitlist promotion and ordering policy.
- Late-cancellation windows, penalties, and no-show consequences.
- Recurring generation horizon and any scheduled job.
- Push notifications or reminders.
- Resources/rooms.
- Full payments, entitlement assignment, or balance consumption.

## Acceptance and verification

- PostgreSQL transaction/row lock on each session guards the final available seat and serializes reservation, cancellation, and waitlist entry.
- Migration is checksummed and represented in the Drizzle schema.
- Tests cover session creation, reservation/cancel, full capacity, a deterministic concurrent final-seat race, waitlist in/out, role denial, missing/archived client, archived service, cancelled session, attendance state, audit immutability, generated occurrence separation, and fail-closed entitlement behavior.
- Admin UI has loading/error/empty states, accessible dialogs and keyboard focus, compact responsive week/day views, and 2J tokens only.
- Capture the same screen at 1440, 768, and 390 CSS pixels.
- Keep this PR open; independent Claude and Antigravity reviews must evaluate the same final SHA before merge.
- The default runtime does not yet have a client-plan assignment/balance source. Until that source is integrated, the eligibility resolver fails closed and reservation/waitlist writes are rejected; integration tests inject an eligible entitlement resolver and confirm the transaction, capacity, audit, and client-link flows.
