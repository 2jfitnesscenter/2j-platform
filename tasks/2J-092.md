# 2J-092 — Member Reservations UX V2

**Status:** implementation complete; Draft PR, no merge. **Base:** `f8ac76e9f717bf07048a8a1efd730bb57f5bf301`.

## Product contract

The Member flow starts at Inicio → **Reservar clase** and stays inside the existing five-destination Hub navigation. The Member chooses a published service, explores its local calendar by month and day, individually selects one or more concrete sessions, reviews the complete selection, and explicitly confirms it. Every selected session is submitted separately and displays its own confirmed, waitlist, or failed result. A waitlist request is never presented as a confirmed booking.

Members have no recurring-reservation control. No pattern, weekday rule, or automatic series can create future bookings. A multi-session selection contains only sessions the Member explicitly tapped.

## Ownership and reuse

- Platform’s existing calendar sessions, materializer, eligibility resolver, entitlement and document/debt checks, capacity locking, booking and waitlist mutations, cancellation preview/policy, idempotency, notifications, audit, and cohort gate remain authoritative.
- Client IDs and service IDs are used only to address existing self-scoped endpoints. The browser cannot supply another client identity.
- `GET /api/me/booking-services` returns only active services with a published future session visible to the authenticated client, as `{ id, name }`. Session dates remain bounded by the existing 31-day read contract; the UI loads one month at a time.
- `GET /api/me/sessions` and session-detail eligibility are reused. No bulk booking endpoint, booking-domain rewrite, or migration is introduced.
- The waitlist is an explicit per-session choice from the session details and remains distinct from a confirmed reservation.
- Inicio’s Próxima reserva continues to use the nearest future `reserved` booking only. Waitlist entries are excluded; booking and cancellation refresh the self-scoped booking read model.
- Atlantic/Canary remains the display and day-boundary timezone. Browser display uses local-time formatting with `timeZone: 'Atlantic/Canary'`.
- Preview data is fictional; service and calendar selection work locally, and preview performs no API mutations or reads.

## Acceptance

- No new bottom-navigation item; the existing Inicio CTA opens the flow.
- Service-first selection; month grid has previous/next and Hoy controls, today/selected/current-day cues, and session-day markers; selected day shows chronological session cards and availability text.
- Manual multi-selection supports removal and an explicit confirmation screen. The UI processes each session individually and exposes mixed results without implying atomic success.
- Existing booking/waitlist state blocks duplicate selection. Waitlist is described as a request/position, never as a reserved place.
- Upcoming reservations and waitlist entries remain separately visible; reservation cancellation uses the existing server preview and cancellation rules with an explicit 2J confirmation dialog.
- Members without the pilot booking gate or an eligible active entitlement can still browse where the server allows it; mutation controls remain disabled or the server’s existing reason is shown in human language. The server stays authoritative.
- Light/dark use the Hub theme tokens; keyboard focus, status labels, button semantics, live results, and touch-sized controls remain available.
- Admin calendar, Staff booking/scheduling, Training, `2jfitnessapp`, payment flows, and recurrence templates are outside this task.

## Deferred

No booking-window policy, cancellation rule, waitlist promotion rule, payment/debt policy, entitlement model, or recurrence behavior is created here. The UI reflects the existing backend’s exact responses and leaves any unsupported policy to the existing center workflow.
