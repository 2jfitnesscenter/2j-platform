## Preferences contract

One `platform_member_preferences` row is keyed by canonical `person_id` and stores bounded `appearance` (`system|light|dark`), `language` (`es`), and timestamps. The row is created lazily on update. Reads return defaults without requiring an active fee or writing a row. The Member session resolver supplies the client facet; Platform verifies the active person-to-client binding before using the person key. The browser cannot choose either identity.

- `GET /api/me/preferences` returns `{ preferences: { appearance, language } }`.
- `PATCH /api/me/preferences` accepts only a non-empty object containing allowlisted fields. Unknown keys, invalid appearance and unsupported languages are rejected.
- There are no notification preference columns or toggles: in-app operational notices remain available, and Center News remains on Inicio.

## Behavior and limits

`system` follows `prefers-color-scheme`; `light` and `dark` force the corresponding Hub palette. The API is authoritative. A non-sensitive local appearance hint is read before paint and refreshed after a successful server read/save. Preview skips that storage and all API calls; its theme changes stay in component state. Preference failures keep the Hub usable and expose an explicit retry.

Settings remains available to an authenticated Member with no active fee. Account/security shows only the current email and active status, plus the existing pilot logout when that pilot action is enabled. It does not claim production SSO, recovery or passkeys. Privacy points to existing documents/consents in Profile. Training-only settings remain in Búnker; there is no settings deep link, so the page explains the boundary instead of inventing one.
