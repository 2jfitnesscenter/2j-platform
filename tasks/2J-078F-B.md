# TASK 2J-078F-B — Platform canonical Training link lifecycle and receipt recovery

## Goal

Establish Platform's durable canonical link lifecycle using the signed 078F-A Training receipt endpoint. Receipt reconciliation may recover a Platform transaction and create a canonical **pending** link, but it cannot establish a globally active Training link.

> **Platform pending canonical link != globally active Training link**
>
> **pending → active remains impossible until Training ACK exists**

## Scope

- Add an additive migration for canonical link states, proof source references, uniqueness, lifecycle protections, and safe audit actions while preserving legacy `explicit_admin` active/revoked rows.
- Add a strict signed receipt reconciliation client for `POST /api/platform/v1/link-proofs/reconcile`, reusing the existing service-auth canonicalizer and signer.
- Recover only pending transactions using a receipt whose immutable context matches Platform and whose `verifiedAt` is within the original transaction window and no more than 30 seconds in the future.
- Create/replay one Platform canonical link in `pending`, version 1, with method `verified_training_proof`, transaction and receipt references.
- Keep reconciliation internal; expose no public route. Require an active person/auth binding and all three independent gates.
- Audit recovery, pending creation, and actual lifecycle conflicts without receipt payload, challenge, signature, secret, or Training user ID.

## Explicit exclusions

No Training repository edits, Training ACK/mirror, verified-proof activation, remote revocation, SSO, role/entitlement effects, health/training data, production secrets, LIVE activation, or automatic enablement from environment configuration.

## Acceptance criteria

- Pending-but-clock-expired transactions can recover only with authenticated historical proof in `createdAt <= verifiedAt <= expiresAt`; durably cancelled/expired transactions remain terminal.
- Pending → verified recovery and immutable user/receipt persistence are atomic. Already verified/consumed identities are read consistently; mismatches fail closed.
- Canonical pending link creation is idempotent, transactionally sourced, uniqueness-protected per nonterminal person and Training identity, and grants no access.
- Database triggers reject verified-proof insertion as active and reject a pending → active transition. Legacy explicit-admin active/revoked rows and revoke behavior remain compatible.
- All independent lifecycle/service flags default false; no endpoint is added.
- Clean PostgreSQL 17 migration, repeat/checksum validation, full tests, typecheck, build, audit, secret scan, and diff check pass with no new skipped tests.
