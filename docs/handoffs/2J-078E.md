## Audit of the existing boundary

Platform 078C already stores `verified_training_user_id` write-once in `training_link_transactions` in the same atomic database update as `pending → verified`; the migration already checks its state/shape. The internal `createTrainingLinkTransactions().verify()` method already validates the persisted challenge, supplies durable transaction context to an injected verifier, bounds it with an aborting timeout shorter than the remaining transaction TTL, validates the returned opaque ID, and leaves the transaction pending when the verifier rejects or times out. No schema change or public route is needed.

The reusable signing helpers are `canonicalizeTrainingServiceRequest` and `buildTrainingServiceAuthHeaders` in `apps/api/src/training-integration.ts`. The internal verifier contract is `TrainingLinkVerifier` in `apps/api/src/training-link-protocol.ts`. Current service-call and verified-link options are independent and default false; production startup does not set either from environment.

## Implementation target

Add `createRemoteTrainingLinkVerifier()` and wire it as the default internal verifier. Assertion schema is strict `{ v: 1, code }`; the exchange request context is reconstructed exclusively from persisted Platform context, field ordered deterministically, signed using the existing helper, posted only to the fixed Training exchange path, and validated against a strict bounded response. Any remote error/mismatch remains a proof rejection without a persisted subject.

Configuration names are `TRAINING_SERVICE_BASE_URL`, `TRAINING_SERVICE_KEY_ID`, and `TRAINING_SERVICE_SECRET`. They are runtime-only and cannot enable either gate. Add an end-to-end mock receiver that verifies exact signature/request bytes and confirms the transaction becomes verified without creating `training_account_links`.
