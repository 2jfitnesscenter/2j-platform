# 2J-078C — Central auth ↔ person binding and verified Training link foundation

## Scope and state

Platform-only backend foundation, based on `origin/main` `bddac419eed0ccb413d838bbef6d5c8463771b3e`. The implementation adds explicit provider-scoped auth-subject bindings and a short-lived, person-scoped Training link transaction. It does not infer identity from names, email, phone, client/staff facets, or roles, and does not backfill existing actors.

## Implemented

- Additive PostgreSQL migration `0023_auth_subject_training_link_transactions.sql`: `platform_person_auth_subjects` and `training_link_transactions`, foreign keys with restrictive deletion, uniqueness, state/expiry checks, immutable identity and terminal-state triggers, no hard delete/truncate, and append-only audit actions.
- Admin-only `identity.people.manage` endpoints explicitly create and revoke auth-subject bindings. Subjects are opaque, provider/version scoped, never echoed in responses, and a revoked subject cannot be reassigned in V1. This lifetime uniqueness is a conservative V1 restriction, not a product identity rule.
- Five-minute one-time challenge generation, 256-bit random value, SHA-256-only persistence, request-id replay protection, person-bound cancellation, database-authoritative timestamps, concurrency-safe state transitions, and audit events without challenge or assertion data.
- Strict `TrainingLinkChallenge/v1` and `TrainingLinkTransactionReceipt/v1` response DTOs. A replay never recovers the raw challenge. No canonical Training link is created by a transaction.
- Hardened dormant service-client boundary and request-signature helper: strict origin allowlist, HTTPS outside explicit loopback tests, validated person UUID/path, no redirects, bounded and typed response parsing, end-to-end timeout, and deterministic request-bound signing canonicalization.

## Deliberately not implemented

Central auth provider/runtime, passkeys, SSO, UI, Training-side changes, remote proof verifier, remote ACK, active canonical link creation, entitlement enforcement, credentials, and LIVE provider traffic. No changes were made to `2jfitnessapp` or the Training repository.

All three server options default OFF: `trainingLinkingEnabled` (existing local admin foundation), `trainingVerifiedLinkingEnabled` (new challenge flow), and `trainingServiceCallsEnabled` (future outbound service calls). Turning on verified-linking alone does not enable outbound calls; there is no environment-variable activation path.

## Contract and operational notes

- Self-service resolution is an injected authenticated-subject resolver and defaults to unavailable; callers cannot submit `personId`.
- The raw challenge is returned only once. A same-request replay returns `challenge: null`; cancel the pending transaction and begin a new request if the caller lost it.
- Signatures use UTF-8 canonical bytes with seven newline-separated fields and no trailing newline: `2J-SERVICE-AUTH-V1`, key id, canonical UTC timestamp, UUID request id, uppercase HTTP method, canonical path plus query, and lowercase SHA-256 body digest. Replay-window validation and constant-time signature verification belong to the future receiving service.
- V1 reserves one auth subject mapping per provider+subject for its full lifetime, including after revocation, preventing subject reassignment.
