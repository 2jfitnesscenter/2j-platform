# TASK 2J-096 — Clients + Client 360 foundation

## Objective

Deliver a professional, server-backed client directory and operational Client 360 foundation inside the existing Admin/Trainer shell. Reuse the current Platform client, calendar, entitlement, billing, document, communication, follow-up, and history contracts. Do not add a client-ownership model, duplicate Training, or invent missing domain data.

## Product and privacy rules

- Search, status filtering, ordering, and cursor pagination remain server-side. The UI must not filter a sample or fetch more than the API page limit.
- The directory shows name, profile state, and creation date only. Contact details are not displayed in the list.
- Contact search and profile email/phone/date-of-birth fields require the server-side `clients.manage` grant. Trainer retains name search and authorized operational access.
- Plan/entitlement details remain available under their existing permission. Financial concepts, amounts, and due dates require `billing.read-basic`, including inside immutable purchase snapshots.
- Only backed, permitted Client 360 sections are selectable. Do not show empty future tabs for Training, Progress, or Health; no Training builder or copied training/health data.
- Summary is operational and sourced from current Platform contracts. No “my clients” assignment or ownership was introduced.
- Preserve the existing shell, design tokens, `Atlantic/Canary` date formatting, keyboard access, and responsive behavior.

## Delivered scope

- Refreshed the Clients list with active/archived context, result count, server search, state filter, cursor-based “load more,” compact rows, and a clear profile entry action.
- Replaced placeholder Client 360 tabs with backed sections only: Summary, Plans, Reservations, Payments, Documents, Messages, Follow-up, and History, subject to server capability.
- Added an operational Summary with profile state/date, reservation context, active plan, and links into existing documents/waitlist workflows where available.
- Minimized API list output, restricted contact-based search and PII profile fields to `clients.manage`, and removed finance fields—including purchase-snapshot price fields—from actors without `billing.read-basic`.
- Added regressions for page traversal beyond 100 clients, opaque client-ID deep links, authorized sections, Trainer/Admin privacy differences, and capability-specific financial summaries.
- No schema or migration changes.

## Acceptance

- Admin and Trainer use the existing professional shell. No other app, navigation system, Training repository, or `2jfitnessapp` was changed.
- Search/filter/pagination are backed by current server API behavior and preserve cursor order.
- 360 sections never imply availability for unsupported or unauthorized domains.
- PII and financial data are filtered in the API response, not merely hidden in React.
- Capture the real UI at 1440×900, 768×1024, and 390×844; record overflow, accessibility, and visual evidence in `docs/evidence/2J-096/README.md`.
- Full repository tests, PostgreSQL migrations, typecheck, build, audit, and diff check pass before PR review.

## Out of scope

New ownership/assignment concepts, Training/Health/Progress integration, new client domains or APIs, schema changes, calendar or payments work, new shell/navigation, production infrastructure, and changes to `2jfitnessapp`.
