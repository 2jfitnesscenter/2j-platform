# Design: an explicit, isolated, safe STAGING mode (not implemented, not activated)

Status: **design only.** No code, flag, host, DNS, Caddy, database or secret was created or changed for it. It needs an explicit owner decision and an independent review before any implementation (open question 8 of the architect's review).

## Problem

Today the only safe environments are `development` and `test`: passkeys and provisioning are refused unless `NODE_ENV` is one of them, Platform only accepts loopback member origins, and Búnker has no environment concept. To exercise the real flows (Home on a real host, WebAuthn on real devices, Caddy and proxy headers, SSO across two hosts) a *staging* environment is needed. Running staging with `NODE_ENV=test` on a public host would be worse than not having it (it disables the guards for the wrong reason).

## Principles

1. **Staging is a different, explicit environment, not a weakening of production.** It is enabled by one named profile, never inferred from the host name or from `NODE_ENV`.
2. **Fail closed.** Every precondition below is checked at start-up; if any fails the process refuses to start (no partial mode).
3. **Isolation by construction.** Own hosts, own databases, own secrets, synthetic data only. Nothing in staging can reach a production service and nothing in production can be pointed at staging by configuration alone.
4. **Visible.** A staging process says so in every health response and log line, and the member apps show a banner.
5. **Nothing is enabled by default**, including inside staging: each flag is still opt-in.

## Profile

A new setting `PLATFORM_ENV` (Platform) / `TRAINING_ENV` (Búnker) with the closed set `development | test | staging | production` and **no default** in a deployed container (`production` is the only value the production compose file sets). `NODE_ENV` stays what it is for libraries; the *guards* read the profile.

`staging` additionally requires all of:

| # | Precondition | Checked how |
|---|---|---|
| 1 | `STAGING_ORIGINS`: an explicit allow-list of exact `https://` origins (Home, Búnker, Platform admin). Wildcards, ports other than 443 and any host not under a `STAGING_DOMAIN_SUFFIX` are rejected. The production hosts (`home.2jfitnesscenter.com`, the production Búnker host) are on a **deny-list compiled into the code**. | start-up |
| 2 | The database carries an environment marker: `platform_environment_marker(env='staging')` created by a staging seed script. The process refuses a database without the marker or with a different one, and the production database refuses a `staging` marker. Búnker has the same marker file in its data directory. | start-up, every start |
| 3 | `DATABASE_URL` host and database name match `STAGING_DB_ALLOWLIST` (exact). | start-up |
| 4 | Service keys are *distinct per direction and per environment*, ≥ 32 bytes, with a key id that starts with `stg-`; a production key id (`prod-`) is refused. | start-up |
| 5 | `STAGING_ACK` equals `sha256(sorted(STAGING_ORIGINS) + marker + profile)`: a deliberate human step that ties the configuration to the host list, so a copied `.env` does not silently work elsewhere. | start-up |
| 6 | TLS is mandatory (cookies `Secure`, HSTS on the edge); `PLATFORM_TRUSTED_PROXIES` / `TRUSTED_PROXIES` must be set (exact proxy addresses). | start-up |
| 7 | NTP/chrony healthy on both hosts (clock offset below 2 s); each service exposes `clockOffsetMs` in its authenticated health. | start-up warning + readiness probe |

What `staging` changes relative to `production` and nothing else:
- the passkey and provisioning guards accept the profile `staging` (not only development/test);
- member origins may be the allow-listed `https` staging hosts instead of loopback;
- WebAuthn RP ID must equal the exact staging Home host (same exact-host rule as today; the parent domain is still refused);
- synthetic-data banner and a response header `x-2j-environment: staging`.

What `staging` never allows: a production origin, a production database, a production key, real PII, outbound e-mail/push/payments (the integrations with external providers are replaced by fakes or disabled), or running without the marker.

## Data

Synthetic accounts only (legacy, legacy-linked, shadow, enforced free / other fee / Fuerza, suspended, revoked, provisioned, admin/trainer), generated by a staging seed script that refuses to run without the marker. Never a copy of production; if a production-shaped copy is ever wanted it must be anonymized by a reviewed script first (not part of this design).

## Tests required before it can be implemented (each must exist and pass)

1. Start-up refuses: missing profile, `staging` without each precondition (one test per row above), production hosts in `STAGING_ORIGINS`, a `prod-` key id, a database with the wrong or no marker, a wide `TRUSTED_PROXIES`.
2. `production` profile still refuses passkeys, provisioning and non-loopback member origins exactly as today.
3. Exact-host RP ID tests with the staging Home host (parent and sibling refused).
4. A staging build cannot be coerced into production by editing environment variables alone (marker + deny-list + ACK).
5. Differential suite (`api/scripts/legacy-differential.mjs`) passes with the profile set to `production` and to `staging` for legacy users.

## Operational pieces (outside the code, need the owner)

Separate hosts and DNS names, Caddy with the safe `header_up` rules of `docs/runbooks/2J-INT-proxy-and-rate-limits.md`, per-environment secret store, backup/restore rehearsal of the Búnker data directory, log shipping without secrets/PII, alert on "Platform unreachable for more than N minutes", rollback plan (flags off, per-user mode back to shadow/legacy, restore). None of these was touched.

## Open decisions for the owner

Which hosts/domains; who runs staging, QA and the independent audit; whether real-device WebAuthn testing is wanted before any production rollout (recommended: yes); whether a time-box is set after which staging is destroyed.
