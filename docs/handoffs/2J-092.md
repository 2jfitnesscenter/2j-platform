# Handoff — 2J-092 Member Reservations UX V2

**State:** implementation complete; Draft PR only, not merged.
**Base SHA:** `f8ac76e9f717bf07048a8a1efd730bb57f5bf301`.
**Branch:** `codex/2j092-member-reservations-v2`.
**Scope:** Member Hub calendar/reservation UX and one self-scoped service-read endpoint.

## Implementation

- The Inicio “Reservar clase” action remains the entry point; bottom navigation remains Inicio, Búnker, Tienda, Perfil, Ajustes.
- Member sees active services that have a future published session visible to their own client context. The API response contains only service id/name. Session reads stay self-scoped and bounded to one month per request.
- The booking view now provides month navigation, a month grid with today/selected/session-day markers, and a selected-day chronological session list. Session details load the existing authoritative eligibility response.
- Every reservation or waitlist request is individually chosen from session details. Members may select and remove multiple explicit sessions, then confirm the full selection. The client sends one existing idempotent mutation per session in sequence and records per-session outcomes; it does not use a hidden automatic retry.
- Waitlist enrollment is a separate explicit selection and result. It does not enter Inicio’s Próxima reserva.
- Cancellation reads the existing cancellation preview and presents its server-provided policy summary in a 2J dialog before using the existing cancellation mutation. Waitlist exit has a separate confirmation.
- The no-active-entitlement/pilot-gate states keep account access and schedule browsing where available, map known backend reasons to member-facing Spanish, and keep the server authoritative for every mutation.
- Preview contains fictional services and sessions for confirmed, available, nearly full, full/waitlist, and existing waitlist states. Selection is local; the preview does not call the API.
- `apps/api/src/client-app.ts` adds `GET /api/me/booking-services`, returning only active service `{ id, name }` entries with a future scheduled session in an active area visible to the authenticated client. No schema migration was needed.
- No Member recurring-booking controls or recurrence creation code were added. Staff/Admin recurrence behavior is untouched.

## Reused engine and boundary

Reuses `/api/me/sessions`, session-detail eligibility, `/api/me/bookings`, cancellation preview, per-session reservation/waitlist/cancel mutations, existing idempotency, cohort gate, eligibility resolver, capacity/concurrency rules, audit, and notifications. Does not add a bulk transaction or duplicate booking domain. No changes to Training, `2jfitnessapp`, Admin calendar, or Staff scheduling.

## Review notes / known bounds

- The service list is constrained to future published sessions because the current platform has no separate Member-facing service catalog contract. The session-detail API remains the final eligibility authority.
- Multi-session operations are intentionally per-session, not atomic. The result screen reports each outcome independently.
- No new entitlement, cancellation, booking horizon, or automatic waitlist policy is defined.
- P0/P1/P2: none known after local validation. The only validation bound is that the browser journey used deterministic intercepted synthetic responses rather than a live authenticated pilot session; server behavior was exercised against PostgreSQL integration fixtures. Independent re-review and exact-head CI remain pending.
